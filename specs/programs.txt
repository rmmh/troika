NATIVE PROGRAM OVERLAYS
===============================================================================

Web, terminal and IRC are separate program subsets. Forth belongs to the web
program; IRC and terminal images do not include Forth or HTTP. Program overlays
reuse the same physical Machine RAM and are disk files, not additional ROM,
banked memory, a host executable cache or host protocol implementations.

The first implementation provides a protected native core containing block I/O,
FAT/checking, and a segmented loader. programCore.ts places it contiguously in
ordinary middle code RAM starting at -3631. The linker excludes that exact
reservation from program placement and binds shared calls to the core's native
addresses. Margin code requires an explicit option; programs using margin for
history (IRC) must leave it out of their code allocation.

A program file contains:
  PRG, version 1, entry address, segment count (1..4), checksum
  then segment count repetitions of: destination, length, data[length]
The checksum is the balanced-tryte wrapping sum of entry, segment count, all
segment destinations/lengths and data. Segments are sorted, nonoverlapping and
nonempty; each stays wholly inside one ordinary code extent outside the core.
The entry must belong to a loaded segment. Reserved buffers are stored as zero
cells in the file. No file header is retained as an extra executable allocation.

program_exec receives a counted FAT path in A/B. The caller tail-jumps after
quiescing connections, devices and open file handles. The loader masks interrupts
with -9841 (zero enables them), disables disk callbacks, resets the native stack,
reads through native FAT, validates destination ranges and copies the segments.
Only exact EOF, valid entry and matching checksum authorize transfer. It clears
1337..5467 (old network, document and language state), resets S and enters the
new program. Filesystem state remains in its normal allocation. Programs own
initialization of screen, scratch, URL state, devices and their own code data.

A failed replacement may already have overwritten part of the old program.
It always transfers to the protected program_recover controller with a negative
status; it never resumes the replaced program or executes the invalid image.
The caller/controller path and recovery code must live in the protected core
or be consumed completely by fs_lookup before program copying starts. This is
an integrity check for trusted native programs, not authentication or a sandbox.

Evidence:
  nativeProgram loads A, then replaces it with B through the same guest loader,
  reads multi-block/multi-segment images, clears A's application state, and
  exercises checksum, kernel overlap, entry, truncation and wrapped-range errors.
  firmwareLink checks placement and rejects overlapping/non-code extents and
  external symbols inside the program's writable code range.
  terminalProgramWorld loads the real terminal from a disk file, then performs
  DHCP, routed DNS/stream traffic, keyboard echo, disconnect and reconnect.
  Only the core is initially installed in RAM in that test.

programMenuWorld also verifies fresh durable IRC source ports across reloads.
programMenuWorld exercises the native selector with physical keys: 2 loads
terminal, F1 disconnects, F2 returns to the selector, and 3 loads IRC on that
same CPU/NIC. IRC F2 sends QUIT before exit (or exits after bounded retry
exhaustion), drains pending TX and returns to the selector. Missing files show
a native recovery screen. Terminal and IRC link without code in the margin;
IRC reserves that space for its bounded chat history. No browser/Forth modules
are resident in either program.

Remaining integration:
  - Web program linking with its subordinate compile/interact/file phases.
  - Production world/debugger/CLI controls and checkpoint compatibility.
The existing world terminal command still uses the browser's disk phase until
this integration is complete. Successful independent image linking does not
by itself prove the complete web program plus loader fits.
