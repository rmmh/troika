TROIKA SHARED WORLD EXECUTION
===============================================================================
Status: deterministic coordinator, packet/block hardware and a runnable native
starter world implemented. Coherent whole-world save/replay remains open.

The world has one monotonically increasing cycle clock. All NICs sample it;
CPU count never scales elapsed time. A frame takes 6561 world cycles and a
disk read/write takes 6561 (FLUSH 27), starting when its command is accepted.
The current implementation requires safe-integer cycle timestamps and raises
an explicit simulation-limit error before exceeding that representation.
This limit is earlier than exhausting the full three-tryte tick counter; it
does not wrap or truncate either counter. No host wall clock drives deadlines.

At a timestamp, complete NIC transmissions in lexicographic full three-tryte
interface-identity order, then block operations in stable machine-ID order,
then process CPU boundaries in stable machine-ID order. Delivery copies frames
only within the sender's physical LAN; forwarding belongs to native firmware.
The hardware order above also defines equal-time events across device classes.
Devices latch sticky events immediately, but CPU IRQ entry waits for that
machine's next instruction/sleep boundary. Local display/audio IRQs and network/
disk IRQs join the same pending-line priority decision at that boundary.

Instructions remain atomic interpreter operations, not a microcoded bus model.
Their architectural/MMIO effects commit at the start boundary; their measured
cycle cost reserves a busy interval. Local device ticking and IRQ dispatch
are deferred until its completion. An external event arriving during that
interval cannot execute a handler early. CPU cycles can therefore lead world
time by the currently reserved instruction/IRQ-entry interval; this is explicit
scheduler state, not a second device clock. IRQ entry reserves its normal two
cycles before handler instructions begin. Standalone Machine.step/run retain
their existing synchronous cycle/device behavior.

Sleeping CPUs advance to the next local timer/device boundary, a physical
network/disk event, or the requested simulation horizon. They do not spin one
CPU cycle at a time. Hardware delivery at a sleep expiry is visible before
the CPU's timer continuation. Paused-world hotplug is observed at the current
boundary when execution resumes. No deadline passes while world time is paused.
Advancing one large interval or many smaller intervals must produce identical
machine, device and clock state for the same external actions.

World topology is configured before execution. A machine has at most Q/R NICs
and one B controller; interface identities are unique across all LANs. Link
up/down and disk insertion/removal use the device APIs at a paused timestamp.
The coordinator owns NetworkFabric.advanceTo and externally clocked block
advance; callers must not separately advance those devices behind the world.
Host test fixtures can inject frames, but production services cannot substitute
host routing, protocol decisions, storage lookups or page/Forth execution.

Snapshot/replay acceptance must preserve CPU RAM/cycles/sleep and in-flight
instruction reservations, all peripheral queues/cursors/events/generations,
pending writes, attached media, fabric time and ordered external actions.
Serial counter images cannot be restored independently of live old traffic.
No snapshot feature is claimed until this complete state is captured and
replayed, including the device state needed by browser displays and input.

RUNNABLE STARTER WORLD
-------------------------------------------------------------------------------
Run npm run world for the terminal front end, or npm run world -- --smoke for
one boot and a printed guest screen. By default each run starts fresh disks.
Add --server-disk PATH to retain noticeboard posts across command sessions
and --client-disk PATH to retain downloaded files and local directories.
--archive-disk PATH retains files published on files.world:
  npm run world -- --server-disk ./server.disk --client-disk ./client.disk --archive-disk ./archive.disk
Each launch cold-boots new CPUs, peripherals and traffic; this is not a live
world snapshot. The web world is available at /world.html and through the
root debugger's World option, including live guest memory inspection.

The scenario in src/world/starter.ts assembles nine native images: browser,
BBS server, archive server, door station, camera/alarm security station,
TELNET echo server, DHCP server, DNS server and router.
Two LANs connect them. The
browser acquires 1.2.7 through DHCP, resolves bbs.world through remote DNS, and
fetches the home page from 1.3.2 through the router. The host initially formats
media and configures hardware. It waits for the file server to finish its
checked mount, then queues a physical boot key. Guest startup performs DHCP,
DNS and HTTP; the host does not implement service decisions or look up files.
All phase replacements read trusted native images from the browser disk.

The home page links to a Forth lab, a file library, news, a noticeboard and
Guess the Digit, plus an independent Files World site.
In the lab, LOAD copies the initial field into displayed text; editing and
activating the form invokes a local SUBMIT handler that copies the new field.
The server does not handle that event. The library serves a readme from disk.
The noticeboard stores posts in its guest disk file and serves the updated
page after each POST. The forum index links to independent predefined discussion topics.
Use /home to return to /index on the current site, including from a plain
file or empty HTTP error response. Console open URL provides address entry;
back-history controls are outside the network.txt baseline.

Terminal input is physical text-device input. Type a line to insert text;
a blank line or /enter activates the focused link/input/button. /next and
/previous traverse focus; /home returns to the current site home. /left,
/right, /backspace, /delete, /up and /down
send the corresponding key cells. Prefix literal slash text with a second
slash (//path inserts /path). /quit exits. The host prints the 27x27
mode-T screen, stripping palette attributes; it does not render page records.
Time advances deterministically until the guest completes each input action,
then pauses while waiting for another command. This is not a wall-clock loop.

npm run firmware:report includes every starter image with startup code and the
browser's reusable phase slot. The production-scenario test drives physical
keys across routed navigation, local Forth submission and file viewing, while
checking each linked image against guest code RAM. Additional services, fuller shell and
browser controls and coherent persistence still require implementation.

Each discussion topic accepts one msg field of 1..54 text cells. /app/post
selects /board, /app/game selects /games, and /app/code selects /build. Its
native handler selects a trusted /public topic file, appends a padded counted
text record and atomically replaces the file before serving it. Submitted
punctuation and newlines remain literal record contents. The old board may use
at most 1200 wire cells before appending; a full page advances to the next
provisioned page, with 409 when no further page is available. Invalid
application fields return 400, unknown routes 404, and disk failures abort the
unpublished replacement. There are no user accounts, timestamps, edit/delete
operations or automatic retention policy yet.

createStarterWorld accepts optional serverDisk/clientDisk/archiveDisk physical images for a cold
boot and exposes attached disk media. A test posts twice, destroys the old
CPUs/traffic, boots a fresh world using that disk, and reads both posts through
native HTTP. This proves guest-file persistence; it is not a coherent live
snapshot. With --server-disk, the CLI checkpoints the server disk after boot
and each completed input action, once the client is idle, the server has no
open filesystem handle and its block controller is idle. A failed action does
not replace the previous host checkpoint. With --client-disk, it also checkpoints
client media after the controller is idle and no mutation handle remains. Read
and directory enumeration handles may stay open for paginated output. Archive checkpoints also wait for its handle and block controller to be idle.
Disk checkpoints are individually atomic, not an atomic multi-disk transaction.
Unsaved machine disks are fresh on restart. No live CPU, timer, network or peripheral state is restored.

Server and archive disk containers are exactly 81*243 signed little-endian 16-bit cells;
tryte range and size are checked before boot. Native firmware still validates
FAT and volume identity. Missing files start with the initial media for that role;
malformed files fail rather than being reformatted. Checkpoints write/fsync a
new file in the same parent directory, then rename it over the old container.
The parent directory must already exist. A .lock file prevents cooperating
CLI sessions from writing the same disk simultaneously. Normal exit and errors
release the lock; forced termination may leave one. Confirm its process has
exited before removing a stale lock. This checkpoint format does not replace
whole-world snapshot/replay or guarantee recovery of an interrupted action.

GUESS THE DIGIT
-------------------------------------------------------------------------------
The game at /game is an on-disk PAGE 1 document whose C record contains all
rules. LOAD initializes seventeen Forth variables; SUBMIT validates a single
digit, compares it with the target, updates text and chooses another target
on a round win. The sequence is deterministic native arithmetic, not host
randomness. A low/high guess shows < or >, a round win shows =, and nine wins
finish with !. Empty, multi-character and out-of-range guesses show ? without
changing the score. Replace the previous digit with Backspace. Home and a new
visit restart the game; scores are local to the current page.

The server only returns the page file. No game input is POSTed, and no host
code evaluates a guess or chooses a target. Tests play all nine rounds through
physical keyboard input, check invalid input and finished-state behavior, and
reload the page to verify reset. The compiled page remains inside the existing
729-cell script arena and 27-variable limit; client resident RAM is unchanged.
Including the game and forum routes, the complete BBS image now uses 10784 cells.
Saved server images retain their existing files; new starter content appears
on fresh initial media, without silently overwriting a retained noticeboard.

Use /console (physical F2) to open the local file console. It discards the
current page and loads its own native disk phase. Commands include dir, type,
del, mkdir, rmdir, cls, help, exit, get and open. Paths are absolute; dir alone lists
/. For example, type get /readme /copy, then a blank line to execute; enter
type /copy, then another blank line to read the
saved file. get http://bbs.world/readme /docs/readme also works after
mkdir /docs. URLs may be relative to the retained site origin or absolute.
All command parsing, HTTP transfers and atomic file replacement run on guest
CPUs. Failed downloads report a numeric error and preserve old destination
contents. Directory and file output paginate; a blank line continues. /home
or exit returns to the site's home page. Client media, including downloaded
files, lasts only for the running world unless --client-disk is supplied.

Client disk containers prepend an ASCII header, TROIKA DISK 1, a space, a
64-character lowercase SHA-256 firmware identity and a newline. The identity
hashes JSON of the linked client resident chunks and the initial client disk
cells, which include all linked native phases. This binds saved native code
addresses to the exact build. A mismatch fails before boot and preserves the
container. Use the matching build or a fresh client disk; guest-file migration
between incompatible builds is not implemented. Server containers remain raw
and retain their existing format. The fingerprint is a compatibility check,
not authentication of arbitrary native code. All roles use the same atomic
container replacement and session locking. If opening either disk fails, all
locks acquired by that launch are released.

INDEPENDENT ARCHIVE SITE
-------------------------------------------------------------------------------
files.world resolves to 1.3.4 and runs on its own native CPU and volume 5 on the
server LAN. Its 9488-cell image serves /public/index, /public/readme, /public/game
and /public/sample through the same native HTTP/FAT service as the BBS. It has
its own Host policy and a native sharing handler. Its media starts fresh
unless --archive-disk is supplied. The sample contains signed binary trytes; download it with
get /sample /sample in the console. type reports -115 on non-text content.

From the BBS, follow Files World or use /console, open http://files.world/index,
then a blank line. open accepts relative or absolute URLs. Bad URL/DNS/transport
responses return to the console; accepted pages run the normal compiler and
Forth LOAD pipeline. On the archive site, /home and relative get /readme use the
archive origin. An absolute download from bbs.world leaves that origin intact.
The archive's BBS link performs a real cross-site navigation back. The scenario
waits for both application servers to finish native mount/check before booting
the client. All production role images are included in npm run firmware:report.

FORUM TOPICS
-------------------------------------------------------------------------------
The BBS home page links to /forum, an index of General noticeboard, Game
discussion and Building Troika. Each topic has five linked disk-backed pages and
reply form; All topics returns to the index. A fixed native dispatch table
maps the three application paths to trusted files, so a posted field cannot
choose an arbitrary output path. Replies remain counted literal T records,
never executable C records. Each page enforces the existing
1200-cell pre-append bound; a full topic returns 409. Unknown routes return
404 and invalid/empty fields return 400. Topic replies persist with
--server-disk; cold-boot tests verify isolation and native HTTP retrieval.
These three sections are predefined. Public named topics are described below;
nested threads, accounts, moderation and post deletion remain open. Existing
saved disks retain their contents; fresh initial media contains the new topic pages.

LOCAL BROWSER ERRORS
-------------------------------------------------------------------------------
After a navigation, response parse or page script error, native startup loads
/console and displays the numeric error with F1: home guidance.
The failed page and Forth dictionary are discarded. Home uses the last accepted
origin; an absolute open URL also works when the initial page failed before
any origin was accepted. There is no automatic retry or POST replay.
The reusable browser library retains its sticky negative result until a caller
chooses recovery. The starter distinguishes this state (-1) from a terminal
startup/recovery-image failure (-2). The CLI stops only for the latter; ordinary
browser failures leave the user in a working native console. A missing system
image or unusable disk may prevent error rendering and remains terminal.

PUBLIC TEXT-FILE SHARING
-------------------------------------------------------------------------------
Files World's Share a text file link opens /share. Enter a name of 1..10
lowercase letters, digits or underscores and a text value of 0..54 cells.
Publish sends the compact native form to /app/share. The native handler accepts
exactly name and text, builds a confined /public/shared/name path, and atomically
creates or replaces that file. It serves the published contents as plain text.
The public URL is http://files.world/shared/name; the console can download it
with get /shared/name /local-path while Files World is the accepted origin.

Names are public and replaceable by any user; the form states this explicitly.
There are no accounts or per-file owners. Empty text creates an empty file.
Unknown application routes return 404, invalid names/fields return 400, no disk
space returns 507 and other storage errors return 500. Unpublished failures
preserve the previous file; a cleanup failure after publication may return 500
with the new file already visible. Shared contents never select a page MIME
type, so text resembling PAGE/C records stays inert. Native tests verify this
through direct filesystem reads and live browser responses.

--archive-disk uses the same raw, locked, atomically replaced disk container as
--server-disk. A cold-boot test publishes and overwrites a file, downloads it to
the client, then recreates the world from archive media and retrieves it again.
The form is bounded text sharing. Console PUT supports larger raw payloads
as described below; ownership remains unimplemented.

SHARED-FILE CATALOG
-------------------------------------------------------------------------------
Browse shared files opens /catalog. A native directory walk emits a PAGE 1
response with Home, up to 18 file links and Next when another eligible file
exists. /catalog1 is the first page; /catalog2 through /catalog5 continue the
walk. Home returns to the archive index. Enumeration follows physical directory
order, not alphabetical order; it skips directories and names longer than ten
cells because those cannot be addressed under /shared/name. All names created
by the sharing form are eligible. Five pages cover the filesystem's maximum
81 directory entries. Out-of-range catalog suffixes return 404.

The catalog is generated afresh for every request and never modifies media.
It uses the existing 1458-cell server page arena; at most 21 page records and
748 wire cells are emitted. The directory handle is closed before sending.
The HTTP service streams this stable buffer with the same native flow control
as disk files. It does not cache an index on disk, so newly published files are
visible immediately and a full disk can still be listed. There is no host
filesystem lookup or page construction on the request path.

SELECTED-LINK DOWNLOADS
-------------------------------------------------------------------------------
Focus a file link and press F3, or issue /download in the CLI. The native console
opens with get and the complete URL already entered. Append an absolute local
destination and press Enter. In the CLI, type //copy to insert /copy literally,
then a blank line to execute. F1 (/home) cancels destination entry and returns
to the site's home page. The previous page is discarded when the console opens.
On input fields, buttons or pages without links, F3 does nothing. The file
library and archive home page advertise this shortcut. Publication still waits
for a complete successful response and uses atomic filesystem replacement.

WEB WORLD
-------------------------------------------------------------------------------
Run npm run dev and open /world.html (also linked from the machine debugger).
The web entry point assembles the same native starter world in a Web
Worker. The host displays the client's physical text framebuffer and forwards
keyboard cells. DHCP, DNS, routing, HTTP, filesystem operations and page/Forth
execution still run on the native CPUs. Screen text exposes a plain transcript
of that framebuffer; it is not a separately parsed page.

Click the display to type; Escape releases keyboard focus. On-screen buttons
provide navigation, activation, backspace and F1/F2/F3 shortcuts. Pause stops
all machines and simulated time; Resume continues the same session.
Restart with fresh disks terminates the worker and creates fresh initial media.
Closing or restarting the page discards unsaved disk changes. Save disks
downloads the client, BBS and archive media together; Restore disks replaces
the session and cold-boots those media. It restores files and posts, not CPU
state, a running page, game state or network traffic. No automatic browser
storage is used. Worker or terminal firmware failures are shown as a stopped
state with a restart control.

Saving suppresses new keyboard input and waits up to 100 million simulated
cycles for an idle client, no phase load, no server filesystem handles, no
client mutation and no pending disk operation on the three saved drives. A
paused world can save at this safe point; otherwise resume/finish the operation
and retry. The media are copied synchronously at one simulated instant. The
CLI uses the same safe-point predicate for its individual disk checkpoints.

The bundled format is ASCII "TROIKA WORLD DISKS 1 ", 64 lowercase hexadecimal
SHA-256 digits, LF, then client/server/archive disks in that order. Each disk
has exactly 81*243 signed little-endian 16-bit cells in -9841..9841. The program
desktop uses "TROIKA WORLD DISKS 2 " with a 243-block client followed by
81-block server and archive disks, using the same cell encoding. The hash
binds client firmware using the same fresh resident-chunks/initial-media JSON
descriptor as the CLI client disk format. Wrong size, header/build or tryte
range rejects the restore before replacing the current session. This is a
compatibility check, not authentication or a media-content checksum. Guest
filesystem validation still applies when the restored machines boot.

Web hashing requires Web Crypto (localhost or HTTPS). The bundled format is
distinct from the CLI's individual disk files. Service configuration, server
programs, DHCP/DNS/router media and network traffic start fresh; all old traffic
is discarded before retained endpoint counters are used. Firmware migration
and import of individual CLI disks are not implemented.

LOCAL FILE COPY
-------------------------------------------------------------------------------
In the console, copy /source /destination copies a regular file on the mounted
client volume. Both paths must be absolute; the destination parent must exist.
The destination is created or atomically replaced. Empty files, binary cells,
multiple blocks and self-copy are supported. There are no wildcards, recursive
copies, drive selectors or overwrite prompts. The existing 180-cell console
line limit applies to the command and both paths together.

The browser loads /filecopy into the same 1906-cell phase slot, copies via
native FAT and block I/O, then reloads /console with the result. The network
pump remains resident and runs during disk waits. Source data uses the existing
243-cell filesystem buffer; six cells in inactive Forth state hold copy metadata.
A retained source chain descriptor is walked while atomic replacement owns the
single filesystem handle. The old source remains reachable until publication,
including self-copy; its data are never overwritten during the copy.

Copy requires enough free space for the complete new file before the old
destination is freed. Disk-full errors abort unpublished blocks and preserve
the old destination. Storage failure after publication can report an error
with the new file already visible, as with other atomic replacements. I/O and
media failures invalidate the mount; corruption revokes checked-mount status.
Copy is synchronous guest work and has no interactive cancellation command.
The new native image changes client checkpoint compatibility: older client
media require their matching build or fresh disks.

FORUM PAGINATION
-------------------------------------------------------------------------------
Fresh BBS disks provision pages /board through /board5, /games through /games5,
and /build through /build5. The unsuffixed URL is page one; suffixes 2..5 select
later pages. Next page and Previous page links navigate through normal native
HTTP GET requests. Later pages display their number and contain an independent
blank reply form, including pages that have no replies yet.

The application routes likewise accept /app/post2..5, /app/game2..5 and
/app/code2..5. A POST starts at its selected page and scans forward until the
old file is no more than 1200 wire cells. It appends one 60-cell literal record,
atomically replaces only that page and serves the page receiving the reply.
Earlier pages remain unchanged. No page is allocated during a POST: missing
later pages on older media or a full page five return 409. Suffixes 0, 1, 6..9,
multiple digits and non-digits are not application routes. GET MIME selection
explicitly recognizes the paginated topic paths; unrelated files stay plain.

The five-page limit is a routing/storage bound, not a space reservation. All
three topics share the 81-block server disk and need temporary replacement
space, so storage exhaustion can occur before every page fills. Existing saved
disks retain their original pages and links; there is no automatic migration.
Use a fresh server disk to obtain all pages. The application needs eight
protocol-state cells (2508..2515), a 14-cell path in existing scratch and the
same 1260-cell maximum reply buffer. BBS firmware occupies 10784 code cells,
using explicit optional margin beyond the 9666 resident cells and leaving 1717
total code cells. Client RAM is unchanged.

TRUST LAB
-------------------------------------------------------------------------------
Fresh BBS disks link their home page to /trust, a lesson about treating forum
replies as text and public uploads as untrusted data. Its three fields hold a
preview sample and two short answers. Check copies the sample into a bounded
54-cell T record and updates a score out of two. Both operations execute in
native Forth; there is no host grading, source evaluation or form POST. Empty,
non-digit and multi-character answers earn no point. Reloading resets the lab.

Markup-like text and strings resembling page records remain literal preview
contents. They cannot add records, change the compiled dictionary or execute
source. /trustnotes explains counted text, explicit MIME selection and the
cross-site scripting trust boundary. It is a normal plain-text file that can
be viewed or downloaded. This lab demonstrates correct data handling; it does
not reproduce an exploitable site or certify a site's security from quiz scores.
The trusted page has 18 records, three inputs and ten Forth variables, and
compiles within the existing 729-cell script arena. No client firmware or RAM
allocation changes are needed. The explicit BBS MIME entry occupies seven table cells.

LOCAL RENAME
-------------------------------------------------------------------------------
ren /path newname changes a file or directory's basename within the same parent.
The source path must be absolute and cannot be root. The new basename is 1..18
valid filesystem name cells, without a slash; console input normalizes to
lowercase. Existing destinations, including the unchanged name, return -20
without overwriting anything. Cross-directory moves are not supported.

Rename rewrites one directory block atomically. It does not allocate blocks,
copy file data, change FAT chains or rewrite a nonempty directory's children.
It works on a full medium or full directory, and cold boot sees either the old
name or the new name. Files retain their size and data. Invalid arguments and
read-only writes preserve the old directory; hardware/media failures retain
the filesystem's existing mount-invalidation behavior.

Copy, rename, delete, mkdir, rmdir and write share /filecopy (1467 of 1906 cells).
The resident dispatcher passes operation 4 for copy, 5 for rename, 8 for
delete, 9 for mkdir 10 for rmdir, and 11 for write. Rename uses
seven inactive Forth cells and at most 171 cells of the inactive script arena
to build the destination path. The full client reserves 12382 code cells,
leaving 119. Client disk checkpoints require the matching firmware build.

Console uploads
---------------
put /local/path http://files.world/shared/name uploads a local file to the
archive. A relative URL uses the currently accepted site. Names use 1..10
lowercase letters, digits or underscore. For example, download with
get http://files.world/sample /sample, then run
put /sample http://files.world/shared/mine. The same command replaces an
existing name. Empty files and raw signed trytes are preserved, and uploaded
files appear in the archive catalog. Public names have no ownership controls.
The console reports success only after the server response completes; HTTP
rejections show their status (for example error 405 on a file-only server).
There is no automatic retry. Pause/Resume pauses the whole simulated world;
console input is processed after the transfer. Retained archive disk media
preserves uploads through a cold boot. This uses /upload in the same native
phase slot, with a single filesystem block buffer.

TAKEAWAY
-------------------------------------------------------------------------------
The BBS home page links to /take, a second native Forth game. Start with 21
stones, remove one to three per turn, and take the last stone to win. The bot
leaves a multiple of four when possible and otherwise takes one. Input must
be a single digit 1..3; invalid input leaves the pile and bot move unchanged.
The status is . during play, ? after invalid input, W after a player win and
L after a bot win. Finished games ignore further moves. The Restart link or
a fresh visit resets the pile, status and bot display. Backspace edits a move.

All validation, strategy and display updates execute in the page's compiled
Forth on the client. The page uses 18 variables and 13 records inside the
existing arenas; native client code size is unchanged. /takerules serves plain
text instructions and strategy that can be downloaded through the file console.
Live tests play wins and losses, exercise invalid input and restart, verify
unchanged compiled source/dictionary and balanced stacks, and download/read
rules. There is no server score, remote grading or persistent game state.
New pages are initial media content; retained server disks are not migrated.

Console disk space
------------------
free prints the number of free blocks, total physical blocks and block size
(243 cells). It takes no arguments and runs a read-only native FAT scan. A
fresh client disk has 31 free blocks out of 81; files and filesystem metadata
use the rest. Copies, downloads and atomic replacement can need temporary
space in addition to the final file size. Use free after del or rmdir to see
space reclaimed. The command reads mounted media, not a host-maintained count.
Mutations run in /filecopy. With the expanded help screen, /console uses 1713
cells while leaving the resident RAM allocation unchanged.

Comparing shared files
----------------------
sum /path shows a native rolling checksum plus the number of data blocks and
cells used in the last block. For example, get http://files.world/sample /a,
then run sum /a before sharing it with put. After downloading another copy,
run sum on that path and compare all three values. The command accepts binary
signed cells as well as text and never changes the file. It closes its handle
before returning to the prompt, including when a read fails. This small
checksum is for accidental-change checks, not authentication or protection
against intentional tampering; different files can have the same result.

Creating local files
--------------------
write /note Hello World creates /note with exactly Hello World as its content.
Run type /note to read it, sum /note to compare it, or
put /note http://files.world/shared/note to publish it. Repeating write replaces
the file atomically. write /note with no text empties it. Text capitalization
and spaces after the first path separator are preserved; commands and paths
remain lowercase. There is no implicit newline, quoting, or escape expansion.
The command is for short single-line files within the 180-cell console input
limit, not a multiline editor. Creation requires an existing parent directory
and enough temporary space to retain an old file until publication succeeds.


PUBLIC NAMED TOPICS
-------------------------------------------------------------------------------
The forum index links to /topics, a native directory of public named topics.
/newtopic accepts a name of 1..10 lowercase letters, digits or underscores and
an initial message of 1..54 cells. Creation writes /public/t_name atomically;
existing names return 409. /t_name serves the page, whose reply form appends
literal counted text through /app/replytopic. A missing topic returns 404 and
invalid fields return 400. Exhausted replacement space returns 507 instead of
resetting the connection, for both predefined and named topics. There are no
accounts, ownership or moderation.

Each named topic is a single bounded page: old content over 1200 cells rejects
further replies with 409, and successful appends never exceed 1260 cells.
Names and messages share the existing server page arena and filesystem buffer.
Replies stage only the new 60-cell record in page RAM. Native fs_append copies
the old chain through the shared 243-cell filesystem buffer into an unpublished
replacement, then publishes it atomically. Ten inactive Forth cells at
5225..5234 hold append state; the old page no longer needs a 1200-cell RAM copy.
The descriptor supplies the pre-append length bound. Cold boots at each disk
write boundary see either the complete old file or the complete new file.
Unlike the three predefined sections, named topics do not roll into more pages.
All topics share the 81-block disk and need temporary atomic replacement space.
The fresh BBS has 8 free data blocks; capacity is not reserved per topic.

/topics and /topics1..5 list 18 matching files per page, filtering invalid names
and directories. Filesystem enumeration and page generation run on the guest
CPU. Names become links only within the reserved /t_ namespace. Replies remain
literal text even when they contain page-record syntax. Cold boots retain both
topic contents and their generated directory. Saved disks are not migrated to
add the new-topic form or forum navigation; fresh initial media includes them.


CONSOLE HELP
-------------------------------------------------------------------------------
The help command shows syntax for every local and network command, including
copy, rename, literal writes, raw PUT uploads and checksums. Its 21 lines fit
within the physical 27-row display without pagination or a separate page load.
The short startup banner remains available on entry; help provides the details.
The text also explains absolute paths, replacement and empty-write behavior,
case preservation, keyboard shortcuts and the non-cryptographic checksum.
The console phase uses 1713 of its 1906 cells; resident code still has 119 cells
free. The larger disk image leaves 31 free blocks on the fresh client medium.


TEMPLATE EXECUTION LAB
-------------------------------------------------------------------------------
The home page appends a Template lab link at /xsslab. Its unsafe and literal
fixtures accept the same src field (0..54 cells) and persist their generated
pages on the BBS disk. /app/xunsafe writes the value as a C source record;
/app/xsafe writes it as a counted T text record. The supplied harmless LOAD
sample copies the input into the page's unchanged marker. That changes the
marker only in the unsafe page; the fixed page shows the source as literal text.
Both field values remain counted data. The flaw is choosing an executable
record type for untrusted input, not escaping or a broken record parser.

This is a deliberately flawed stored-XSS analogue inside the guest Forth VM.
The host browser never evaluates the field, and the guest's compilation,
address and instruction budgets still apply. Normal forum and upload handlers
do not use this template. Each fixture is a public replaceable slot, without
accounts or ownership. Invalid input returns 400; disk exhaustion returns 507.
Each replacement is atomic and at most 268 cells (two disk blocks).

The unsafe editor at /xedit is an immutable initial file. Submitting opens the
saved /xunsafe preview; the index also links directly to that saved page.
If invalid source breaks the preview, F1 returns home and the clean editor can
replace it. /xsafe is the literal preview. /xssnotes is downloadable plain text.
Both previews persist across a server-disk cold boot. Tests run the same sample
through both forms, verify the different native execution results, cold-boot
persistence, invalid-source recovery, literal newlines and allocation failure.

The BBS now uses 10784 code cells, leaving 1717 including explicit margin.
Fresh BBS media has eight free blocks; replacing both initial previews uses two
more permanently and needs temporary replacement space. This lab and all
forum topics share that capacity. Client resident and phase allocations are
unchanged. The larger virtual-device ecosystem remains unfinished; the optional
NPC browser added below runs within its own memory budget.


NATIVE DOOR STATION
-------------------------------------------------------------------------------
A seventh CPU serves door.world at 1.3.5 on the remote LAN, with its own 81-block
volume (identity 6) and NIC identity 60. The BBS home page links to it. Like the
other HTTP services, it performs routing, stream framing, form validation and
response generation in guest firmware. The CLI and web worker wait for all
three HTTP listeners before powering on the browser and report door boot errors.

GET / or /index generates current Door and Bell status, a code/state form, and
links to /bell, /manual and the BBS. POST /app/door requires exactly code and
state fields. State is a single 0 (closed) or 1 (open); code must exactly match
the three-cell demo code. Validation precedes any device-state change. Wrong
codes return 403, malformed fields return 400 and unknown actions return 404.
The plain downloadable maintenance manual deliberately publishes the scenario
code, 314. This fixture demonstrates server-side checking, not secret storage,
authenticated users or real-world access control.

POST /app/bell requires only ring=1 and increments a public counter that
saturates at nine. It never opens the door. Successful actions rewrite the
response path to /index; the response hook generates the updated status after
the POST, so users see the change immediately without another GET.

State occupies three guest protocol cells at 2508..2510: door-open flag, bell
count and validated requested state. There is no host device-state callback or
host grader. Opening/closing/ringing does not write persistent files. A cold
world boot resets the door closed and bell to zero. CLI and web checkpoints
continue to save only client, BBS and archive disks; door device state is not a
live snapshot or persistent fourth checkpoint disk.

The complete door image uses 8613 of 9666 resident code cells (1053 free), with
no optional margin. Its generated page uses the existing server page arena;
no client RAM or phase allocation changes. Initial door media has 65 free
blocks. The optional NPC browser is described below; the larger device
ecosystem remains unfinished.

Optional native NPC visitor
---------------------------
`npm run world -- --npc` or world.html?npc=1 adds an optional CPU at 1.3.6,
NIC identity 70, with its own volume 7. The first physical power key is queued
once the player has reached a checkpoint-safe state. Native firmware then
opens http://bbs.world/board, executes its normal bounded Forth LOAD hook,
and revisits after 2187 network ticks. Failed visits use the same native
backoff; no host timer selects pages or retries. The address is static and
DHCP messages are ignored. The three-client BBS can still return BUSY when
all slots are occupied; the NPC records failures and retries.
Cells 2325..2328 report completed visits, errors, last status, and attempts.
The browser shares the player's six disk phases but links them against its
own resident symbols. firmware:report measures its complete resident image
and the shared 1906-cell phase slot. The NPC's disk and
volatile state are not part of the three-disk checkpoint; restore cold-boots
it. A native integration test executes a page hook, observes a later player
post, disconnects its NIC, checks backoff, and verifies recovery after reconnect.

Keyboard and embedded world debugger
------------------------------------
The root debugger's World button opens the same world application as
world.html. Switching back to Machine debugger preserves the world session;
the world continues running unless paused. Use Focus display (Tab then Enter)
to direct physical keys to the guest. Tab/Shift+Tab navigate guest controls,
Enter activates, F1 opens home, F2 opens the file console, and F3 downloads.
Escape returns focus to Focus display. The canvas is outside the page tab
sequence, so another Tab proceeds to page controls instead of recapturing keys.
Screen transcripts and all page controls are keyboard accessible.

Inspect machines opens the root debugger's memory map, address/label lookup,
registers and disassembly for the selected live world CPU, including the NPC
when enabled. These panels are read-only snapshots taken by the worker between
scheduler chunks. MMIO inspection does not consume input or acknowledge
interrupts. Pause freezes the whole world and provides a stable snapshot;
switching the machine while paused still refreshes its memory. Guest code can
therefore be examined without creating a separate, unrelated emulator run.

Server interrupt waits
----------------------
Starter DNS, DHCP, router, BBS, archive and door loops now use netWait.asm.
NIC events wake CPU interrupt line 4; the handler only returns to the caller
of H and leaves interrupts masked until the next wait. Initialization enables
RX, TX-complete, overflow, link-change and command-error events on both configured
interfaces. The wait rechecks all RX queues and existing RX ownership before H;
an already-pending interrupt closes the queue-check/sleep race.

Idle DNS/router waits are indefinite when no network output is pending. DHCP
lease expiry is checked when requests arrive, so its idle wait needs no timer.
Pending network operations wake at most one network tick later even without
an interrupt. HTTP waits indefinitely only with no connection, output or
control response pending. Active parsing/output continues immediately; blocked
sends and live/closing/tombstone connections use the bounded timer fallback.
The player and NPC loops are unchanged. No host protocol scheduler is added.

World inspection now shows whether the selected CPU is ready, sleeping with
a timer, or waiting indefinitely for an interrupt. Machine cycle counters
include time spent asleep; increasing cycles alone do not indicate busy polling.
On the measured host, server waiting reduced home-page boot from 7.5s to 2.4s;
guest cycles remained about 7.1 million. Tests inject a packet between queue
inspection and H, wake either NIC, check timed wakes and zero idle instruction
execution, and bound idle work in the complete production world.

Native chat demo
-------------------------------------------------------------------------------
The web world adds a dedicated chat CPU and four native Troika client CPUs.
CHAT/1 (chat.txt) provides nine server sessions and three rooms. Each client has
its own NIC, native request/retry loop, keyboard command parser and history.
Ada runs a small native ELIZA-style responder; Lin and Sam have game/workshop
dialogue and idle chatter. JavaScript supplies physical keyboard input and
renders guest memory; it does not generate packets or choose bot replies.
The Chat client and Room selectors, Message field, Send, Join/Leave and Retry
controls are keyboard accessible. The server and all four clients appear in
the normal world memory inspector. Chat starts fresh after restart or restore.
Programmatic worlds opt in with createStarterWorld(source, {chat:true}); normal
world.runCycles() advances every client and server. There is no extra chat.step
call. Pausing world execution pauses protocol retries and autonomous chatters.

Download control-plane service
-------------------------------------------------------------------------------
Long native downloads can span repeated DHCP renewals. While an unpublished
replacement holds the filesystem handle, the download phase services low
serial-range headroom before the next network iteration. It parks the partial
243-cell block and 23 lookup/handle cells in private phase storage, temporarily
releases the handle, refills the durable /net.seq counter on the already checked
system volume, then restores the download. The FAT cache/tag remain coherent;
no mount scan or orphan check is allowed over the unpublished chain. The service
also runs while waiting for the next body frame. It preserves the accepted page
and origin, and does not publish the file before validated HTTP EOF. Tests force
repeated refills, including a low-tryte boundary crossing, between body frames.

Native console network utilities
-------------------------------------------------------------------------------
ping HOST sends one native ICMP echo with hop limit 27. trace HOST (or traceroute
HOST) sends fresh probes with increasing hop limits 1..27, stopping at the
first echo, unreachable reply or terminal local error. Each row shows the hop,
reporter address and E (echo), U (unreachable), T (time exceeded), or * (timeout).
Ping also prints elapsed network ticks. Results remain on the text screen until
Enter; long traces paginate after twenty probes. F1 cancels during DNS/probe
waits or at a result screen. Cancellation returns to the console. Hostnames use
native DNS; bracketed tribble numeric hosts bypass DNS. For example:
  ping bbs.world
  traceroute files.world
  ping [__N.__P.__O]
Only a host is accepted, not a URL, port, path or additional argument.

probeConsole.asm and probe.asm run in the same /upload disk phase as PUT.
The native dispatcher uses an explicit signed argument count to distinguish
PUT from console utilities; malformed PUT input cannot select another command. No resident browser code or additional phase slot is added.
The probe engine uses 5225..5249, its UI uses 5250..5257, URL/DNS use their normal
arenas, and decimal output uses existing scratch. There is no retained trace
log or host protocol state. The mode closes/drains the prior stream, services
DHCP while waiting, and preserves the accepted origin. Browser networking must
not consume a probe reply before this phase has matched it. The phase owns
physical key polling until Enter/F1; disk checkpoints remain unavailable while
it is active. Tests cover routed replies, DNS failure, numeric targets, silent
peer timeout, cancellation, subsequent browsing and guarded code/stack writes.


Native program desktop

Native camera and alarm station
-------------------------------
security.world is a combined virtual appliance at 1.3.13 on the remote LAN,
with its own native CPU, NIC and 81-block disk (system volume 13). The BBS home
page links to it. /index renders a 3-by-9 text camera and the alarm state.
The simulated subject is @; action 0 advances it one cell, wrapping after 27.
This public action simulates physical motion. It increments a count saturated
at nine and latches the alarm if armed. Reading or refreshing the page is
read-only. The browser never computes appliance state or camera pixels.

The native /app/device form requires exactly code and action fields. Action 1
arms, 2 disarms and clears, and 3 acknowledges while keeping it armed. These
commands require demo code 271, deliberately published in /manual as a small
maintenance-code exercise. Invalid codes, fields, commands or routes leave
state unchanged. Action 0 requires the code field to exist but accepts an
empty value. The manual explains that this is a simulation credential.

Three native HTTP clients have separate transport and response contexts;
POST admission serializes mutations. Retried transport DATA cannot repeat a
motion action. Tests run three actual browser CPUs, drop a response packet,
and verify distinct response snapshots with exactly three moves. ICMP uses
the independent existing responder; NIC interrupts and timed retry waits
allow the station to sleep while idle.

Measured linked allocation is 11806/12501 cells, including 1266 parked stream
cells and 649 parked HTTP cells. Generated pages are 266 cells at 2552..2817;
a second HTTP context occupies 2818..3466, ingress 3467..3709. Shared device
state occupies 2508..2512; ICMP, filesystem, scratch and the native stack keep
their existing allocations. The third response context is included in the
linked 649-cell bank. Guarded integration observed 11/243 native stack cells.

The station is available in CLI and browser worlds, including live debugger

existing three saved disks and do not retain camera/alarm state; live device

Live-state capture foundations (not a world snapshot feature)
------------------------------------------------------------
Machine.captureCpuState/restoreCpuState copy RAM, cycle count, sleep state,
interrupt-dispatch enable and deferred device cycles. An instruction's CPU/MMIO
effects are already committed at its start; restore preserves the pending
completion rather than executing the instruction again. These methods must be
called at a host boundary, outside device callbacks. They deliberately do not
capture attached devices or the World scheduler and are not a disk-checkpoint
replacement.

DeviceEvents preserves sticky bits, enables and the pending IRQ edge separately.
TextDevice preserves unread input, transcript and control/activity state.
DisplayDevice preserves scanline/fractional timing, per-line scroll latches,
current/previous/latched pad state and an undelivered pad edge. Restore performs
validation before mutation and does not tick hardware or dispatch interrupts.
Captured arrays are independent copies. CPU RAM and display state must be
restored together; display restore does not synthesize writes into backing RAM.

stateCapture exercises instruction-completion replay without duplicate MMIO,
IRQ dispatch after a reserved instruction, finite/infinite sleep, unread text,
sub-scanline display replay and rejection without partial mutation. These
records currently have no exported file format. NIC/fabric capture is covered
below, as are block media and pending writes. World hardware integration is
described at the end, followed by ordered external actions. File/UI integration
remains before claiming the complete feature.
Unsupported attached peripherals must be rejected rather than silently omitted.


Network capture/restore component
--------------------------------
NetworkFabric.captureState records fabric time and every configured interface's
identity, MMIO slot, segment, link state, staging/retained TX, completion time,
three RX ring entries and their cursors/head/count, result/drop counters, clock
latch and complete DeviceEvents state. Frames are independent copies. Restore
requires an equivalent existing topology, validates every port before mutation,
and does not deliver packets, generate link changes or flush interrupt edges.
Equal-time completions still use interface-identity order, independent of the
order in which the destination fabric's ports were configured.

networkState replays simultaneous in-flight transmissions into a wrapped RX
queue with one free slot: the same frame is accepted and the other increments
the drop counter. It also covers edited staging versus retained TX, an old
clock latch, pending IRQs, link-down cancellation, immutable capture arrays and
atomic rejection of a bad late port/topology. These are component APIs only;
CPU/serial-media state and network traffic must be restored together by the
future World integration. They do not expose a live snapshot file or UI yet.


Block capture/restore component

BlockMedium captures geometry, read-only status and a copy of every stored
tryte. Restore requires matching geometry and read-only status, validates the
whole image before mutation, and can restore read-only media without issuing
guest writes. Restoring an existing object preserves scenario references.

BlockDevice captures all 27 mounted-unit references as indices into a caller-
supplied shared media pool, generations, change masks, completion events,
transfer buffer/cursor, selected unit/address, result/completion registers,
generation latch and pending operation with its remaining cycles and frozen
write data. The pool allows multiple units/controllers to reference the same
medium. Controller restore installs references directly; it does not simulate
hotplug, raise events, flush interrupts or complete an operation. All fields are
validated before mutation, including pending-operation/media consistency.

blockState verifies deadline-exact pending writes, pending reads, flushes,
read-only media restore, shared mounts, partial read cursors, hotplug-cancelled
operations, pending IRQ delivery, reset cancellation, independent snapshot
buffers and atomic rejection of malformed controller/media state. These are
component APIs: World now captures/restores the media pool together with
controllers and the other supported hardware, as described below. External
action integration is described below; a serialized file format and UI remain
unfinished.


World hardware capture/restore integration

World.captureState now collects host CPU state, scheduler phase/deadline/sleep
start, text/display state, NIC/fabric state and block-controller/media state
at a host boundary. World.restoreState requires equivalent configured hosts,
peripheral attachment order and network topology. It validates all records
before changing live hardware, including consistency between CPU clocks and
instruction/sleep/interrupt reservations. It preserves supported local device
objects and existing compatible medium objects, including shared mounts.
Unknown peripherals and replacement of coordinated NIC/disk devices are errors.

The media pool records mounted and previously captured media, allowing a
snapshot to rewind hotplug without inventing media-change events. A restored
medium absent from the current pool is allocated from its saved geometry.
Scenario references to compatible existing media remain valid; references to
media removed by restoring another timeline must not be used as mounted media.

worldState compares complete hardware captures after replay across instruction,
sleep and interrupt-entry boundaries, pending network delivery and disk I/O,
display timing and hotplug. Late malformed records are rejected without partial
restoration. starterReplay uses the production native program-overlay world
with IRC peers, rewinds boot I/O and physical text input, and compares all
captured hardware state after repeating the same elapsed intervals and inputs.

This remains an in-memory API. Ordered external actions are covered below; a
serialized snapshot format and user-facing live save/load still need integration
before the complete snapshot/replay acceptance gate is met.


Ordered external action timeline

World.queueAction accepts text trytes, gamepad state, NIC link changes and
media insertion/removal at the current or a future world timestamp. Targets
and values are validated before enqueue; mutable text arrays are copied.
Each entry has a monotonic sequence number. Equal-time hardware completions
occur first (NICs, then disks), followed by actions in enqueue order, followed
by CPU boundaries. Action timestamps participate in scheduler wakeups, so a
sleeping machine can observe an input without waiting for another hardware
event. No guest protocol work is performed by an action.

The queue and next sequence counter are part of WorldState. Restore validates
ordering, unique sequence numbers, future timestamps, media references and
peripheral targets before any live state changes. registerMedium gives queued
mount actions a shared-pool reference even before a medium is attached.
Completed actions need no separate log to resume a snapshot: their effects are
in the captured hardware; only pending actions and the counter are restored.

Web/CLI player keys, NPC power-on keys and chat controls use this queue. Native
chat clients still parse physical text and execute all protocol work themselves.
Disk-only checkpoints reject a world with pending actions; they cannot preserve
a live input timeline. Direct device APIs remain available for test fixtures,
but future external actions must use queueAction to be included in snapshots.

worldActions verifies same-time insertion order, chunk-independent replay,
queued media mounting, link and gamepad changes, late invalid-action rejection,
and write completion before same-time media removal. starterReplay now captures
future keyboard actions during native program-world boot and after browser
startup and replays them without manually re-injecting the input.
