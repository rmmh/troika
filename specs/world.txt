TROIKA SHARED WORLD EXECUTION
===============================================================================
Status: deterministic coordinator, packet/block hardware and a runnable native
starter world implemented. Coherent whole-world save/replay remains open.

The world has one monotonically increasing cycle clock. All NICs sample it;
CPU count never scales elapsed time. A frame takes 6561 world cycles and a
disk read/write takes 6561 (FLUSH 27), starting when its command is accepted.
The current implementation requires safe-integer cycle timestamps and raises
an explicit simulation-limit error before exceeding that representation.
This limit is earlier than exhausting the full three-tryte tick counter; it
does not wrap or truncate either counter. No host wall clock drives deadlines.

At a timestamp, complete NIC transmissions in lexicographic full three-tryte
interface-identity order, then block operations in stable machine-ID order,
then process CPU boundaries in stable machine-ID order. Delivery copies frames
only within the sender's physical LAN; forwarding belongs to native firmware.
The hardware order above also defines equal-time events across device classes.
Devices latch sticky events immediately, but CPU IRQ entry waits for that
machine's next instruction/sleep boundary. Local display/audio IRQs and network/
disk IRQs join the same pending-line priority decision at that boundary.

Instructions remain atomic interpreter operations, not a microcoded bus model.
Their architectural/MMIO effects commit at the start boundary; their measured
cycle cost reserves a busy interval. Local device ticking and IRQ dispatch
are deferred until its completion. An external event arriving during that
interval cannot execute a handler early. CPU cycles can therefore lead world
time by the currently reserved instruction/IRQ-entry interval; this is explicit
scheduler state, not a second device clock. IRQ entry reserves its normal two
cycles before handler instructions begin. Standalone Machine.step/run retain
their existing synchronous cycle/device behavior.

Sleeping CPUs advance to the next local timer/device boundary, a physical
network/disk event, or the requested simulation horizon. They do not spin one
CPU cycle at a time. Hardware delivery at a sleep expiry is visible before
the CPU's timer continuation. Paused-world hotplug is observed at the current
boundary when execution resumes. No deadline passes while world time is paused.
Advancing one large interval or many smaller intervals must produce identical
machine, device and clock state for the same external actions.

World topology is configured before execution. A machine has at most Q/R NICs
and one B controller; interface identities are unique across all LANs. Link
up/down and disk insertion/removal use the device APIs at a paused timestamp.
The coordinator owns NetworkFabric.advanceTo and externally clocked block
advance; callers must not separately advance those devices behind the world.
Host test fixtures can inject frames, but production services cannot substitute
host routing, protocol decisions, storage lookups or page/Forth execution.

Snapshot/replay acceptance must preserve CPU RAM/cycles/sleep and in-flight
instruction reservations, all peripheral queues/cursors/events/generations,
pending writes, attached media, fabric time and ordered external actions.
Serial counter images cannot be restored independently of live old traffic.
No snapshot feature is claimed until this complete state is captured and
replayed, including the device state needed by browser displays and input.

RUNNABLE STARTER WORLD
-------------------------------------------------------------------------------
Run npm run world for the terminal front end, or npm run world -- --smoke for
one boot and a printed guest screen. By default each run starts fresh disks.
Add --server-disk PATH to retain noticeboard posts across command sessions
and --client-disk PATH to retain downloaded files and local directories.
--archive-disk PATH retains files published on files.world:
  npm run world -- --server-disk ./server.disk --client-disk ./client.disk --archive-disk ./archive.disk
Each launch cold-boots new CPUs, peripherals and traffic; this is not a live
world snapshot. The web world is available at /world.html; the existing web
debugger remains a separate single-machine interface.

The scenario in src/world/starter.ts assembles six native images: browser,
BBS server, archive server, DHCP server, DNS server and router. Two LANs connect them. The
browser acquires 1.2.7 through DHCP, resolves bbs.world through remote DNS, and
fetches the home page from 1.3.2 through the router. The host initially formats
media and configures hardware. It waits for the file server to finish its
checked mount, then queues a physical boot key. Guest startup performs DHCP,
DNS and HTTP; the host does not implement service decisions or look up files.
All phase replacements read trusted native images from the browser disk.

The home page links to a Forth lab, a file library, news, a noticeboard and
Guess the Digit, plus an independent Files World site.
In the lab, LOAD copies the initial field into displayed text; editing and
activating the form invokes a local SUBMIT handler that copies the new field.
The server does not handle that event. The library serves a readme from disk.
The noticeboard stores posts in its guest disk file and serves the updated
page after each POST. The forum index links to independent predefined discussion topics.
Use /home to return to /index on the current site, including from a plain
file or empty HTTP error response. Console open URL provides address entry; back-history controls
remain unfinished.

Terminal input is physical text-device input. Type a line to insert text;
a blank line or /enter activates the focused link/input/button. /next and
/previous traverse focus; /home returns to the current site home. /left,
/right, /backspace, /delete, /up and /down
send the corresponding key cells. Prefix literal slash text with a second
slash (//path inserts /path). /quit exits. The host prints the 27x27
mode-T screen, stripping palette attributes; it does not render page records.
Time advances deterministically until the guest completes each input action,
then pauses while waiting for another command. This is not a wall-clock loop.

npm run firmware:report includes every starter image with startup code and the
browser's reusable phase slot. The production-scenario test drives physical
keys across routed navigation, local Forth submission and file viewing, while
checking each linked image against guest code RAM. Additional services, fuller shell and
browser controls and coherent persistence still require implementation.

Each discussion topic accepts one msg field of 1..54 text cells. /app/post
selects /board, /app/game selects /games, and /app/code selects /build. Its
native handler selects a trusted /public topic file, appends a padded counted
text record and atomically replaces the file before serving it. Submitted
punctuation and newlines remain literal record contents. The old board may use
at most 1200 wire cells before appending; a full board returns 409. Invalid
application fields return 400, unknown routes 404, and disk failures abort the
unpublished replacement. There are no user accounts, timestamps, edit/delete
operations or automatic retention policy yet.

createStarterWorld accepts optional serverDisk/clientDisk/archiveDisk physical images for a cold
boot and exposes attached disk media. A test posts twice, destroys the old
CPUs/traffic, boots a fresh world using that disk, and reads both posts through
native HTTP. This proves guest-file persistence; it is not a coherent live
snapshot. With --server-disk, the CLI checkpoints the server disk after boot
and each completed input action, once the client is idle, the server has no
open filesystem handle and its block controller is idle. A failed action does
not replace the previous host checkpoint. With --client-disk, it also checkpoints
client media after the controller is idle and no mutation handle remains. Read
and directory enumeration handles may stay open for paginated output. Archive checkpoints also wait for its handle and block controller to be idle.
Disk checkpoints are individually atomic, not an atomic multi-disk transaction.
Unsaved machine disks are fresh on restart. No live CPU, timer, network or peripheral state is restored.

Server and archive disk containers are exactly 81*243 signed little-endian 16-bit cells;
tryte range and size are checked before boot. Native firmware still validates
FAT and volume identity. Missing files start with the initial media for that role;
malformed files fail rather than being reformatted. Checkpoints write/fsync a
new file in the same parent directory, then rename it over the old container.
The parent directory must already exist. A .lock file prevents cooperating
CLI sessions from writing the same disk simultaneously. Normal exit and errors
release the lock; forced termination may leave one. Confirm its process has
exited before removing a stale lock. This checkpoint format does not replace
whole-world snapshot/replay or guarantee recovery of an interrupted action.

GUESS THE DIGIT
-------------------------------------------------------------------------------
The game at /game is an on-disk PAGE 1 document whose C record contains all
rules. LOAD initializes seventeen Forth variables; SUBMIT validates a single
digit, compares it with the target, updates text and chooses another target
on a round win. The sequence is deterministic native arithmetic, not host
randomness. A low/high guess shows < or >, a round win shows =, and nine wins
finish with !. Empty, multi-character and out-of-range guesses show ? without
changing the score. Replace the previous digit with Backspace. Home and a new
visit restart the game; scores are local to the current page.

The server only returns the page file. No game input is POSTed, and no host
code evaluates a guess or chooses a target. Tests play all nine rounds through
physical keyboard input, check invalid input and finished-state behavior, and
reload the page to verify reset. The compiled page remains inside the existing
729-cell script arena and 27-variable limit; client resident RAM is unchanged.
Including the game and forum routes, the complete BBS image uses 9360 cells.
Saved server images retain their existing files; new starter content appears
on fresh initial media, without silently overwriting a retained noticeboard.

Use /console (physical F2) to open the local file console. It discards the
current page and loads its own native disk phase. Commands include dir, type,
del, mkdir, rmdir, cls, help, exit, get and open. Paths are absolute; dir alone lists
/. For example, type get /readme /copy, then a blank line to execute; enter
type /copy, then another blank line to read the
saved file. get http://bbs.world/readme /docs/readme also works after
mkdir /docs. URLs may be relative to the retained site origin or absolute.
All command parsing, HTTP transfers and atomic file replacement run on guest
CPUs. Failed downloads report a numeric error and preserve old destination
contents. Directory and file output paginate; a blank line continues. /home
or exit returns to the site's home page. Client media, including downloaded
files, lasts only for the running world unless --client-disk is supplied.

Client disk containers prepend an ASCII header, TROIKA DISK 1, a space, a
64-character lowercase SHA-256 firmware identity and a newline. The identity
hashes JSON of the linked client resident chunks and the initial client disk
cells, which include all linked native phases. This binds saved native code
addresses to the exact build. A mismatch fails before boot and preserves the
container. Use the matching build or a fresh client disk; guest-file migration
between incompatible builds is not implemented. Server containers remain raw
and retain their existing format. The fingerprint is a compatibility check,
not authentication of arbitrary native code. All roles use the same atomic
container replacement and session locking. If opening either disk fails, all
locks acquired by that launch are released.

INDEPENDENT ARCHIVE SITE
-------------------------------------------------------------------------------
files.world resolves to 1.3.4 and runs on its own native CPU and volume 5 on the
server LAN. Its 9488-cell image serves /public/index, /public/readme, /public/game
and /public/sample through the same native HTTP/FAT service as the BBS. It has
its own Host policy and a native sharing handler. Its media starts fresh
unless --archive-disk is supplied. The sample contains signed binary trytes; download it with
get /sample /sample in the console. type reports -115 on non-text content.

From the BBS, follow Files World or use /console, open http://files.world/index,
then a blank line. open accepts relative or absolute URLs. Bad URL/DNS/transport
responses return to the console; accepted pages run the normal compiler and
Forth LOAD pipeline. On the archive site, /home and relative get /readme use the
archive origin. An absolute download from bbs.world leaves that origin intact.
The archive's BBS link performs a real cross-site navigation back. The scenario
waits for both application servers to finish native mount/check before booting
the client. All six role images are included in npm run firmware:report.

FORUM TOPICS
-------------------------------------------------------------------------------
The BBS home page links to /forum, an index of General noticeboard, Game
discussion and Building Troika. Each topic has its own disk-backed page and
reply form; All topics returns to the index. A fixed native dispatch table
maps the three application paths to trusted files, so a posted field cannot
choose an arbitrary output path. Replies remain counted literal T records,
never executable C records. Each topic independently enforces the existing
1200-cell pre-append bound and returns 409 when full. Unknown routes return
404 and invalid/empty fields return 400. Topic replies persist with
--server-disk; cold-boot tests verify isolation and native HTTP retrieval.
These are predefined topics, not user-created or nested threads. Accounts,
moderation, post deletion and pagination remain open. Existing saved disks
retain their contents; fresh initial media contains the new topic pages.

LOCAL BROWSER ERRORS
-------------------------------------------------------------------------------
After a navigation, response parse or page script error, native startup loads
/console and displays the numeric error with open URL or F1: home guidance.
The failed page and Forth dictionary are discarded. Home uses the last accepted
origin; an absolute open URL also works when the initial page failed before
any origin was accepted. There is no automatic retry or POST replay.
The reusable browser library retains its sticky negative result until a caller
chooses recovery. The starter distinguishes this state (-1) from a terminal
startup/recovery-image failure (-2). The CLI stops only for the latter; ordinary
browser failures leave the user in a working native console. A missing system
image or unusable disk may prevent error rendering and remains terminal.

PUBLIC TEXT-FILE SHARING
-------------------------------------------------------------------------------
Files World's Share a text file link opens /share. Enter a name of 1..10
lowercase letters, digits or underscores and a text value of 0..54 cells.
Publish sends the compact native form to /app/share. The native handler accepts
exactly name and text, builds a confined /public/shared/name path, and atomically
creates or replaces that file. It serves the published contents as plain text.
The public URL is http://files.world/shared/name; the console can download it
with get /shared/name /local-path while Files World is the accepted origin.

Names are public and replaceable by any user; the form states this explicitly.
There are no accounts or per-file owners. Empty text creates an empty file.
Unknown application routes return 404, invalid names/fields return 400, no disk
space returns 507 and other storage errors return 500. Unpublished failures
preserve the previous file; a cleanup failure after publication may return 500
with the new file already visible. Shared contents never select a page MIME
type, so text resembling PAGE/C records stays inert. Native tests verify this
through direct filesystem reads and live browser responses.

--archive-disk uses the same raw, locked, atomically replaced disk container as
--server-disk. A cold-boot test publishes and overwrites a file, downloads it to
the client, then recreates the world from archive media and retrieves it again.
This is bounded text sharing; binary uploads, larger payloads and ownership
remain unimplemented.

SHARED-FILE CATALOG
-------------------------------------------------------------------------------
Browse shared files opens /catalog. A native directory walk emits a PAGE 1
response with Home, up to 18 file links and Next when another eligible file
exists. /catalog1 is the first page; /catalog2 through /catalog5 continue the
walk. Home returns to the archive index. Enumeration follows physical directory
order, not alphabetical order; it skips directories and names longer than ten
cells because those cannot be addressed under /shared/name. All names created
by the sharing form are eligible. Five pages cover the filesystem's maximum
81 directory entries. Out-of-range catalog suffixes return 404.

The catalog is generated afresh for every request and never modifies media.
It uses the existing 1458-cell server page arena; at most 21 page records and
748 wire cells are emitted. The directory handle is closed before sending.
The HTTP service streams this stable buffer with the same native flow control
as disk files. It does not cache an index on disk, so newly published files are
visible immediately and a full disk can still be listed. There is no host
filesystem lookup or page construction on the request path.

SELECTED-LINK DOWNLOADS
-------------------------------------------------------------------------------
Focus a file link and press F3, or issue /download in the CLI. The native console
opens with get and the complete URL already entered. Append an absolute local
destination and press Enter. In the CLI, type //copy to insert /copy literally,
then a blank line to execute. F1 (/home) cancels destination entry and returns
to the site's home page. The previous page is discarded when the console opens.
On input fields, buttons or pages without links, F3 does nothing. The file
library and archive home page advertise this shortcut. Publication still waits
for a complete successful response and uses atomic filesystem replacement.

WEB WORLD
-------------------------------------------------------------------------------
Run npm run dev and open /world.html (also linked from the machine debugger).
The web entry point assembles the same six-machine starter world in a Web
Worker. The host displays the client's physical text framebuffer and forwards
keyboard cells. DHCP, DNS, routing, HTTP, filesystem operations and page/Forth
execution still run on the native CPUs. Screen text exposes a plain transcript
of that framebuffer; it is not a separately parsed page.

Click the display to type; Escape releases keyboard focus. On-screen buttons
provide navigation, activation, backspace and F1/F2/F3 shortcuts. Pause stops
all six machines and simulated time; Resume continues the same session.
Restart with fresh disks terminates the worker and creates fresh initial media.
Closing or restarting the page discards unsaved disk changes. Save disks
downloads the client, BBS and archive media together; Restore disks replaces
the session and cold-boots those media. It restores files and posts, not CPU
state, a running page, game state or network traffic. No automatic browser
storage is used. Worker or terminal firmware failures are shown as a stopped
state with a restart control.

Saving suppresses new keyboard input and waits up to 100 million simulated
cycles for an idle client, no phase load, no server filesystem handles, no
client mutation and no pending disk operation on the three saved drives. A
paused world can save at this safe point; otherwise resume/finish the operation
and retry. The media are copied synchronously at one simulated instant. The
CLI uses the same safe-point predicate for its individual disk checkpoints.

The bundled format is ASCII "TROIKA WORLD DISKS 1 ", 64 lowercase hexadecimal
SHA-256 digits, LF, then client/server/archive disks in that order. Each disk
has exactly 81*243 signed little-endian 16-bit cells in -9841..9841. The hash
binds client firmware using the same fresh resident-chunks/initial-media JSON
descriptor as the CLI client disk format. Wrong size, header/build or tryte
range rejects the restore before replacing the current session. This is a
compatibility check, not authentication or a media-content checksum. Guest
filesystem validation still applies when the restored machines boot.

Web hashing requires Web Crypto (localhost or HTTPS). The bundled format is
distinct from the CLI's individual disk files. Service configuration, server
programs, DHCP/DNS/router media and network traffic start fresh; all old traffic
is discarded before retained endpoint counters are used. Firmware migration
and import of individual CLI disks are not implemented.

LOCAL FILE COPY
-------------------------------------------------------------------------------
In the console, copy /source /destination copies a regular file on the mounted
client volume. Both paths must be absolute; the destination parent must exist.
The destination is created or atomically replaced. Empty files, binary cells,
multiple blocks and self-copy are supported. There are no wildcards, recursive
copies, drive selectors or overwrite prompts. The existing 180-cell console
line limit applies to the command and both paths together.

The browser loads /filecopy into the same 1906-cell phase slot, copies via
native FAT and block I/O, then reloads /console with the result. The network
pump remains resident and runs during disk waits. Source data uses the existing
243-cell filesystem buffer; six cells in inactive Forth state hold copy metadata.
A retained source chain descriptor is walked while atomic replacement owns the
single filesystem handle. The old source remains reachable until publication,
including self-copy; its data are never overwritten during the copy.

Copy requires enough free space for the complete new file before the old
destination is freed. Disk-full errors abort unpublished blocks and preserve
the old destination. Storage failure after publication can report an error
with the new file already visible, as with other atomic replacements. I/O and
media failures invalidate the mount; corruption revokes checked-mount status.
Copy is synchronous guest work and has no interactive cancellation command.
The new native image changes client checkpoint compatibility: older client
media require their matching build or fresh disks.
