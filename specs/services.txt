TROIKA DHCP AND DNS DATAGRAM PAYLOADS
===============================================================================
Status: native DHCP and DNS client/server components implemented and tested.
Complete scenario/application integration and total RAM fit remain unproven.
These are deliberately small Troika protocols, not Internet wire formats.
All offsets are zero-based payload trytes. Require exact used length and zero
frame padding. Validate the entire message before changing any lease/cache.
transport.txt's full address/port/serial matching and routing rules apply.

1. DHCP (SERVER PORT 67, CLIENT PORT 68)
-------------------------------------------------------------------------------
Every message has 27 payload trytes:
  0       version 1
  1       kind: 1 DISCOVER, 2 OFFER, 3 REQUEST, 4 ACK, 5 NAK, 6 RELEASE
  2..4    stable client interface identity, nonzero
  5..7    selected/offered server network address
  8..10   requested/offered client network address
  11..13  default gateway network address, or zero for no route
  14..16  DNS server network address
  17      lease duration in ticks, 81..9841 for OFFER/ACK
  18..26  reserved zero

DISCOVER: fields 5..17 zero. Network source/destination zero, link broadcast.
OFFER: includes server, proposed client, gateway, DNS and lease duration.
REQUEST: includes selected server and requested address; fields 11..17 zero.
ACK: repeats authoritative server/client/gateway/DNS/duration fields.
NAK: identifies server and client; address/configuration/duration fields zero.
RELEASE: includes server and current client address; fields 11..17 zero.
Server messages echo the request's serial A and client identity. Source is
the configured server address, source port 67, destination port 68. Bootstrap
replies use link unicast to that identity and network destination zero.
Once configured, replies may use the leased network destination. The client
accepts only its current transaction serial, identity and selected server.
All DHCP stays on its LAN; routers never forward bootstrap broadcasts.

Client DISCOVER and the subsequent REQUEST are distinct transactions with
fresh serials. DISCOVER uses the common three-send/729-tick query policy.
After OFFER, select that server and REQUEST the offered address with the same
policy. One configured DHCP server per LAN; do not merge competing offers.
No application traffic until a matching ACK is fully validated. The offered
client, server and nonzero gateway must be in the same two-tryte subnet. DNS
may be remote. No lease may assign the all-zero network address.

Server has at most nine lease slots. Each slot is twelve trytes:
  identity (3), address (3), expiry tick (3), state (1), reserved (2).
State 0 free, 1 offered, 2 bound. Expiry uses the wide world clock, never a
wrapping tryte. Offered reservations live 729 ticks. Bound leases use the
configured duration, initially 4860 ticks (60 seconds). Scan nine entries;
no table indexed by every possible host value. A fixture configures at most
nine available host trytes and reserves server/router/static addresses.
Address selection scans the configured pool and active reservations.

Repeat DISCOVER from an existing identity returns its reserved/bound address;
repeat REQUEST for its owned address ACKs it. A successful REQUEST sets a new
expiry. Retransmission may extend a lease but cannot allocate an additional
slot or replace another identity's lease. REQUEST without a matching owned
reservation/binding, invalid subnet, or an exhausted pool receives NAK.
RELEASE frees only a matching identity/address binding; it has no response.
Serials and identity fields are not authentication.

A matching ACK enables a lease, but its lifetime is conservatively anchored at
this transaction's FIRST successfully submitted REQUEST, not ACK reception or
its most recent retry. A delayed ACK must never outlive the server's binding.
Both expiry and renewal are computed from that anchor: duration ticks until
expiry, floor(duration/2) until a fresh unicast renewal REQUEST. If an ACK is
already beyond that conservative expiry, discard it and rediscover. The old
lease stays usable while renewal is pending, never past its original expiry.
A matching renewal ACK establishes a new conservative anchor/duration. NAK or expiry
clears address, gateway, DNS cache and neighbour cache, aborts the stream,
and restarts discovery. Failed renewal does not prolong the old lease.
No rebind/broadcast fallback phase or DHCP relay in this version.

2. DNS (SERVER PORT 53, CLIENT PORT 243)
-------------------------------------------------------------------------------
Query payload:
  0 version 1; 1 kind 1; 2 name length 1..54; 3.. name text.
Exactly 3+length trytes. Source/destination network addresses are configured
unicast addresses. The hostname follows web.txt's canonical lowercase label
syntax; the guest client performs case folding and trailing-dot removal.
No compressed names, suffix search, record-type selection or alias chasing.

Reply payload:
  0 version 1; 1 kind 2; 2 status (0 found, 1 not found, 2 service error);
  3..5 address; 6 TTL in ticks; 7 name length; 8.. canonical name.
Exactly 8+length trytes. Echo the requested name and transaction serial A,
reverse ports/addresses. Found requires nonzero address and TTL 1..9841.
Other statuses require zero address and TTL. Malformed queries are dropped.
Unknown names receive not-found, rather than silent timeout.

A server has at most 27 records, each 63 trytes: length, 54 name cells padded
with zero, three address cells, TTL, four reserved zero. This 1701-tryte table
belongs to the DNS server's own RAM and is included in its firmware fit report.
Reject duplicate names at configuration time. Firmware performs the lookup;
a host Map or host DNS resolver cannot answer packets in the scenario.

Client keeps one cached name/address/expiry in its existing URL/protocol state.
Compare the entire canonical name and three-tryte address. Cache hits are
usable strictly before expiry; replace on another successful query. Do not
cache errors. The common retry policy uses one serial for three identical
sends. Ignore replies with wrong name, serial, endpoint/port tuple or shape.
Do not reset the retry deadline on irrelevant traffic. The browser resolves
names before opening its one stream; numeric addresses bypass DNS only.

3. NATIVE DNS IMPLEMENTATION AND MEMORY
-------------------------------------------------------------------------------
firmware/include/dns.asm validates canonical names and normalizes client input;
dnsServer.asm validates all records (including duplicate names and padding)
before listening, then searches guest RAM and sends routed datagram replies.
Its 27-record table is at 2552..4252, replacing browser page arenas on that
server; metadata uses 2280..2285. A busy single retained TX drops a new query;
the requester retries. The common network poll still handles neighbours.

dnsClient.asm owns one outstanding query and the retained TX buffer until
completion/cancellation. It verifies the full endpoint/port/serial/name tuple,
exact shape and deadline before accepting a reply. Error results are not cached.
It detects changes to its configured address or DNS server while waiting.
Explicit dns_client_cancel invalidates the cache (for lease/link changes).
Protocol metadata is 2290..2320 (31 trytes). Current and cached canonical names
and cached address occupy 6320..6430 (111 trytes of the URL/input allocation);
temporary normalization uses shared scratch. These addresses must not be
reused by future URL parsing while their values are live.

Tests execute normalization, full-table validation, routed resolution, cache
hits/expiry, lost-response retries, three-send timeout and mismatched replies
on guest CPUs, with CPU writes audited against the declared mutable regions.
This component evidence does not prove the full browser or ecosystem fits.

4. NATIVE DHCP IMPLEMENTATION AND MEMORY
-------------------------------------------------------------------------------
dhcpServer.asm uses fourteen protocol metadata cells at 2321..2334. Its nine
12-cell lease slots at 4739..4846 and nine configured host values at 4847..4855
replace a browser's page records on this server. Initialization rejects duplicate
hosts, the server/gateway addresses, zero addresses, invalid duration and DNS
configuration. Other static addresses must be excluded by the scenario pool.
Native scans expire reservations, preserve an existing identity's slot, reject
unowned REQUESTs, and RELEASE only bound identity/address matches.

dhcpClient.asm uses 35 protocol cells at 2344..2378. DISCOVER and REQUEST use
distinct durable serials; retries share their transaction's serial. Configuration
is installed only after a complete matching ACK. A failed renewal stops retries
and waits for original expiry. Link loss, NAK or expiry clears configuration and
neighbour state, then discovery restarts. Irrecoverable serial/clock errors stop
the client with a negative status; start explicitly retries after repair.

Both sides construct DHCP controls in TX scratch, preserving retained application
data. The client requires a native dhcp_lease_lost callback in its application to
clear DNS and abort its stream; tests exercise callback delivery, while complete
application integration remains an open gate. Public service must run throughout
the lease, including during application activity. A blocking serial range refill
is followed by an expiry recheck before renewal can send.

Native tests cover exchange, full tuple/serial matching, retries, bounded timeout,
conservative delayed-ACK handling, odd-duration renewal, release, pool exhaustion,
expiry, link restoration and malformed configuration/messages.
